Types of the hosting

  • Shared hosting - server is shared between the people using it
  • Dedicated hosting - server is dedicated to one application
  • Cloud hosting - is usefull when you want to run the application on different machines. E.g one part of app requires CPU. Application, data, runtime, middleware is managed by you, everythinh else by clud provider
  • Paas stands for Platform as a Service. It is a cloud computing model that gives developers a complete, ready-to-use platform to build, run, and manage applications without needing to build or fix the underlying hardware and software infrastructure.
  • Faas - instead of giving the provider the application, you give the application the set of functions. And the provider takes care of building the app.

DNS and the domain names

  • Resolver (recursive resolver): The middleman that works on behalf of you. Your device asks it a question, and it does all the legwork of finding the answer. It's usually run by your ISP or a public service like Cloudflare (1.1.1.1) or Google (8.8.8.8). It also caches answers so repeat lookups are fast.
  • Root server: The top of the DNS hierarchy. It doesn't know the IP address of www.example.com, but it knows who is responsible for each top-level domain (.com, .org, .lv, etc.) and points you to them. There are 13 root server identities (A through M), each operated by many servers worldwide.
  • TLD server: Responsible for one top-level domain, such as .com. It doesn't know the IP of www.example.com either, but it knows which name servers are authoritative for example.com.
  • Authoritative name server: The final source of truth for a domain. It holds the actual DNS records (A, AAAA, MX, CNAME, etc.) for example.com and gives the real answer.

Lookup step by step

  1. Your device asks the resolver: "What's the IP of www.example.com?"
  2. If the resolver doesn't have it cached, it asks a root server. The root replies: "I don't know, but here are the .com TLD servers."
  3. The resolver asks a .com TLD server. It replies: "I don't know, but here are the authoritative name servers for example.com."
  4. The resolver asks the authoritative name server, which replies with the actual IP address.
  5. The resolver returns the answer to your device and caches it for the record's TTL (time to live).

Deploying the static webpage on the Github pages

  • Make a new GitHub repo (public, unless you have GitHub Pro/Team for private Pages). If you want it at https://yourusername.github.io/, name the repo exactly yourusername.github.io.
  • Otherwise any repo name works and it'll be served at https://yourusername.github.io/repo-name/.
  • Put index.html at the root (or in a /docs folder if you prefer).
  • Keep your linked files (CSS, JS, images, other pages like about.html) in the same relative structure your index.html references them with — relative links (./about.html, css/style.css) work fine.

git init
git add .
git commit -m "Initial site"
git branch -M main
git remote add origin https://github.com/yourusername/your-repo.git
git push -u origin main
  • Go to your repo → Settings → Pages.
  • Under "Build and deployment," set Source to "Deploy from a branch."
  • Choose branch main (or wherever your files live) and folder / (root) or /docs.
  • Save.
  • GitHub will give you a URL like https://yourusername.github.io/your-repo/. It rebuilds automatically every time you push.
